# Concepts

A brief tour of the four ideas the project rests on. None of these are
novel to `rdf-shapes-wasm` — they are W3C standards and a compilation
target — but the rest of the docs assume them.

## RDF

**RDF** (Resource Description Framework) models data as a set of
**triples**: `(subject, predicate, object)`. Each triple is a statement
— "this subject has this property with this value" — and a collection of
triples forms a **graph**. Subjects and predicates are identified by
IRIs; objects are either IRIs or literal values (strings, numbers,
dates). Because every node is globally named, graphs from different
sources merge cleanly.

This is the data model everything else here operates on: queries read
it, shapes constrain it.

## SPARQL 1.1

**SPARQL** is the W3C query language for RDF graphs — the "SQL of the
semantic web". A query describes a **graph pattern** (a set of triples
with variables) and the engine finds every binding of those variables
that matches the data:

```sparql
SELECT ?name WHERE {
  ?person a :Person ;
          :name ?name .
}
```

SPARQL 1.1 adds aggregation, subqueries, property paths, and updates on
top of the original SPARQL 1.0. The query engine here is
[Oxigraph](https://github.com/oxigraph/oxigraph), which implements the
SPARQL 1.1 query specification.

## SHACL Core

**SHACL** (Shapes Constraint Language) is the W3C standard for
*validating* RDF graphs. A **shapes graph** declares constraints — node
shapes and property shapes — and a validation run checks a data graph
against them, producing a **validation report** of conformance and
violations:

```turtle
:PersonShape a sh:NodeShape ;
  sh:targetClass :Person ;
  sh:property [
    sh:path :name ;
    sh:minCount 1 ;
    sh:datatype xsd:string ;
  ] .
```

**SHACL Core** is the constraint vocabulary excluding the optional
SHACL-SPARQL extension. The validation engine here is
[rudof](https://github.com/rudof-project/rudof) (`shacl_validation`),
which implements SHACL Core.

## The wasm artifact

**WebAssembly** (wasm) is a portable binary instruction format with a
sandboxed execution model. Rust compiles to the
`wasm32-unknown-unknown` target, and the result is a single `.wasm`
module that any wasm host can run: a browser, a server-side runtime, or
a CLI host.

The project compiles both engines into one such module. A thin
JavaScript shim (generated by `wasm-bindgen`) marshals values across the
JS ↔ wasm boundary, so callers see ordinary functions. The same bytes
run everywhere — that portability is the whole point.

See [Architecture](architecture.md) for how the crates are split to keep
that portability honest, and how the artifact is built reproducibly.
